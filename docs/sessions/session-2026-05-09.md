# Session 2026-05-09

## Objetivos
- Analizar el problema de autorecuperamiento post-reboot del servidor.
- Reducir la dependencia de Snap en un servidor Ubuntu headless.
- Preparar una migracion reversible para ejecutar Chromium dentro de Docker.
- Mantener intacto el servicio productivo actual hasta validar el contenedor en el servidor.

## Cambios realizados
- Se agrego `Dockerfile` basado en `node:20-bookworm-slim`.
- La imagen instala Chromium por `apt`, no por Snap.
- Se configuro runtime Docker con:
  - `CHROME_BIN=/usr/bin/chromium`
  - `STATE_DIR=/state`
  - `HOST=0.0.0.0`
  - `PORT=3001`
- Se agrego `.dockerignore` para excluir `.env`, estado sensible, backups, logs, `node_modules` y archivos locales.
- Se agrego `compose.yml`:
  - monta `/opt/whatsapp-scheduler/state:/state`
  - publica `${PANEL_BIND:-0.0.0.0}:${PORT:-3001}:3001`
  - permite limitar el bind del panel a WireGuard con `PANEL_BIND=10.0.0.1`
  - configura `shm_size: 512mb`
  - usa `no-new-privileges:true`
  - elimina capabilities con `cap_drop: ALL`
  - usa `init: true`
- Se agrego `deploy/systemd/whatsapp-scheduler-docker.service` como unit alternativo para Docker Compose.
- Se actualizo `docs/DEPLOYMENT.md` con prueba manual, validacion, migracion systemd y criterio para no remover Snap antes de validar Docker.
- Se actualizo `docs/TODO.md`.
- Se actualizo `docs/SESSION_LOG.md`.

## Problemas
- El reboot controlado mostro una linea critica en `systemd-analyze critical-chain` relacionada con `run-docker-netns-abf3d447c169.mount`.
- Los logs del boot anterior mostraron decenas de snaps desmontandose.
- El servidor tiene Snap instalado con paquetes de escritorio como Chromium, GNOME, CUPS y Mesa, que no son deseables para un servidor headless.
- Chromium Snap ya habia generado warnings en el servicio:
  - `xdg-settings: not found`
  - `not a snap cgroup for tag snap.chromium.chromium`
- El uso de Chromium Snap obligo anteriormente a quitar `NoNewPrivileges=true` del unit principal.

## Soluciones
- Se preparo una imagen Docker donde Node y Chromium viven dentro del mismo runtime.
- Chromium queda instalado por `apt` dentro del contenedor, evitando depender del Snap del host.
- El estado sensible sigue persistiendo fuera del contenedor en `/opt/whatsapp-scheduler/state`.
- El unit actual `whatsapp-scheduler.service` no fue reemplazado todavia.
- Se agrego un unit alternativo `whatsapp-scheduler-docker.service` para migrar solo despues de validar el contenedor.
- Se valido localmente:
  - `docker compose config` correcto.
  - `docker compose build` correcto.
  - `docker run --rm whatsapp-scheduler:local chromium --version` confirmo Chromium dentro de la imagen:
    - `Chromium 148.0.7778.96 built on Debian GNU/Linux 12 (bookworm)`
